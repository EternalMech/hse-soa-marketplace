# Первый вариант архитектуры маркетплейса

![C4 Container диаграмма маркетплейса](diagrams/containers.svg)

## Границы сервисов

| Сервис | Домены и ответственность | Почему |
| --- | --- | --- |
| Пользователи | Аккаунты, профили, email, роль покупателя и продавца | Один владелец сведений об аккаунте для остальных частей системы; обе роли могут принадлежать одному аккаунту |
| Каталог и лента | Товары, категории, текущие цены, история просмотров и порядок выдачи | Лента использует данные каталога внутри приложения; меньше сетевых зависимостей и синхронизации копий данных |
| Заказы | Позиции, количества, зафиксированные цены, итог, состояние заказа | Заказ сохраняет условия покупки и существует независимо от успеха конкретной попытки оплаты |
| Платежи | Создание платёжных операций, определение их суммы из заказа и учёт результатов | Платёжная интеграция обновляется отдельно от заказов; требуется согласование их состояний |
| Уведомления | Email о статусах заказов, учёт отправок и повторные попытки | Ошибки доставки не отменяют оплату или изменение заказа; отправку можно обрабатывать независимо |

Получается 5 серверных сервисов и 6 областей ответственности. Отдельно показано веб-приложение для покупателей и продавцов. Каталог и лента объединены, чтобы получать данные товаров внутри одного приложения. Это уменьшает число сетевых зависимостей, но требует совместного выпуска и масштабирования этих двух модулей.

Персонализация использует историю просмотров. Товары из чаще просматриваемых категорий получают приоритет в выдаче. Для пользователя без истории выбрана случайная подборка опубликованных товаров.

## Технологии и допущения

В текущем варианте приняты следующие технические допущения. Они задают основу схемы; конкретные провайдеры и контракты интеграций ещё не определены:

- Веб-приложение на JavaScript, HTML и CSS; конкретный фреймворк пока не выбран.
- Python и FastAPI для HTTP-сервисов, Python worker для обработки уведомлений. FastAPI используется в каркасе сервиса заказов; тот же стек предполагается для остальных HTTP-сервисов.
- Отдельная PostgreSQL-база и отдельные права доступа для каждого сервиса. Сервис не читает и не изменяет чужую базу. Общая база каталога и ленты принадлежит одному сервису. Диаграмма не требует отдельной физической машины на каждую базу.
- RabbitMQ для асинхронных событий.
- Оплата через внешнюю страницу провайдера, получение результата через webhook; почта через внешний SMTP-сервис.
- Сервис уведомлений получает актуальный email через API пользователей. Недоступность этого API задерживает уведомление и требует повторной попытки.

## Основные сценарии

### Выбор товаров и оформление заказа

Веб-приложение синхронно получает ленту и передаёт просмотры в сервис каталога и ленты. Продавец через то же веб-приложение управляет своими товарами. Проверку роли и принадлежности товара выполняет сервер

При оформлении веб-приложение передаёт выбранные товары и количества в заказы. Заказы запрашивают у каталога актуальные сведения, рассчитывают сумму и сохраняют заказ с ценами на момент оформления. Успешный HTTP-ответ содержит номер и состояние уже сохранённого заказа. Оплата и письмо не входят в ожидание этого ответа.

Если каталог недоступен, заказ не создаётся, покупатель получает ошибку и предложение повторить оформление позже. Ранее открытая карточка может содержать устаревшую цену, поэтому её данных недостаточно для оформления.

### Начало и результат оплаты

Веб-приложение передаёт сервису платежей ID заказа. Платежи получают из заказов зафиксированную сумму и состояние, проверяют возможность оплаты и создают операцию у провайдера. Сумма из браузера не является источником истины. Веб-приложение открывает полученную платёжную страницу.

Провайдер позже сообщает результат. Платежи должны проверить подлинность сообщения, сопоставить операцию и сохранить результат, затем передать событие через RabbitMQ в заказы. Платёжные результаты должны включать как минимум успех и отказ. Заказы обновляют состояние, не удаляя заказ из-за отказа оплаты. Если заказы временно недоступны, обновление их состояния задерживается.

При повторной попытке используется сумма зафиксированного заказа. Текущий вариант предусматривает полную оплату заказа. Частичные оплаты, комиссии и возвраты не рассматриваются.

### Уведомление о статусе

Заказы передают событие об изменении статуса в уведомления через RabbitMQ. Уведомления получают email пользователя и передают письмо почтовому сервису. Допускается небольшая задержка доставки. Неудачная отправка не меняет результат оплаты.
